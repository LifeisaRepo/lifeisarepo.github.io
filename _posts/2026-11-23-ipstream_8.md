## Where #7 left off

[IPStreamMedia](https://github.com/LifeisaRepo/UE_IPStream){:target="\_blank"} is the Unreal plugin I'm building to play live RTSP camera streams through Unreal's own Media Player. In [#7](/devlogs/2026/11/22/ipstream_7.html) it finally showed live video, with FFmpeg decoding on its own thread (the worker), and opening a stream stopped freezing the game.

Then I checked what was next on the plan.. After a working player it had four milestones left: move the colour conversion to the GPU, make the player survive things going wrong, get a packaged build and a latency number, and make a demo. The awkward part: when I made the plan in August, I gave this project eight weekends, and those were used up 😬.



## A deadline appears

So I gave the first version, v0.1, a date: **Monday 26 Oct**, ahead of a game-dev expo on the 28th. I was going there to meet people and show them my portfolio, this plugin included. I wouldn't have a PC there, so the demo had to be a screen recording of a packaged build.

To make that date I had to cut the GPU colour conversion. I had already decided that it would be one of the first things I would cut if I ran short on time. Audio got pushed to after v0.1 as well.

A release also needed two things no milestone covered. The camera URL has my password in it, and nobody else can reach my home network anyway, so the URL can't be baked into the build. So the demo needed a screen where you type the URL in, and it had to run as a packaged game, not just in the editor. The plan was to create a packaged build as early as possible, because some problems only show up in packaged builds, and after [#5](/devlogs/2026/09/16/ipstream_5.html) I definitely wasn't going to wait till the last minute.

While working on the URL screen I came across another interesting problem: since it calls *Open Url* directly, `WMF` picked up the `rtsp://` URL by default (it claims `rtsp` too, as we saw in [#6](/devlogs/2026/10/12/ipstream_6.html)). Calling *Set Desired Player Name* (`IPStreamMedia`) before *Open Url* sorted that problem.

## Worked in the editor, failed when packaged

After a build was finally packaged, the first run threw an **"Open Url Failed"** error (obviously!). The log said `avcodec-63.dll` and `avformat-63.dll` failed to load because they "do not exist" 🙃. Both were sitting right there in the folder. `avutil` and `swscale` loaded just fine.

If you read [#5](/devlogs/2026/09/16/ipstream_5.html), Windows error 126 might ring a bell. It also means **"a DLL that this DLL needs is missing"**. Reading the import tables showed that `avcodec` imports `swresample-7.dll`, which the build wasn't copying into the package. `avformat` then failed because it needs `avcodec`. The editor never showed this because the plugin's source folder holds the full set of FFmpeg DLLs, while the package only gets the ones I listed.

I also wanted the GitHub release to carry the plugin on its own along with the demo game. Interestingly, packaging the plugin **dropped the whole FFmpeg folder!** I realised the plugin packager only copies a fixed set of folders, plus whatever `Config/FilterPlugin.ini` lists. So now that file lists the headers, import libs, DLLs and licence files.

Development and Shipping builds both streamed, and **`v0.1-beta`** went out as a pre-release, with the demo and the plugin zip. It played a stream just fine. It just couldn't tell you when something went wrong.

## Telling Blueprint what's going on

That was the next milestone anyway: making the player survive things going wrong. Its checklist was to pull the network cable mid-stream, stop PIE mid-stream, give it a bad URL, and open and close it multiple times in a row, with nothing hanging, crashing or leaking.

Reconnecting already worked (the worker reconnects by itself, and toggling the PC's network adapter brought the picture back every time), and stopping PIE was handled by the thread join from [#7](/devlogs/2026/11/22/ipstream_7.html). The problem was what the Blueprints saw. Back in #6, `MediaOpened` fired the moment I called *Open Url*. With no FFmpeg in the skeleton that was fine, but now it was a lie: it fired before anything had connected. And a dead URL just failed silently, because the worker kept retrying in the background and never told anyone.

The worker can't simply call the engine to report things. It's on the wrong thread, and there's a nastier problem. The facade (the engine layer in front of every player plugin, from #7) holds a lock while it calls our `Close()`, and `Close()` waits for the worker to finish. If the worker ever needed that same lock, both would wait for the other forever resulting in a **deadlock**, and stopping PIE would hang.

So the worker drops ready-made engine events into a queue that it owns (`TQueue<EMediaEvent, EQueueMode::Spsc>`: lock-free, one thread writes, one reads). The player reads that queue in `TickInput`, which runs on the game thread every frame, and passes the events on. Since the queue lives inside the worker, `Close()` throws away any stale news along with the worker. No clean-up code needed.

Now Blueprint actually knows what's going on:

- **Media Opened** fires at the first frame (~1.4 s after *Open*).
- **Media Open Failed** fires for a URL that never connects, after 2 tries (14.1 s). A stream that has never worked is most likely a wrong URL, so it doesn't get to retry forever.
- **Playback Suspended / Resumed** fire around a reconnect. Tested by switching the network adapter off and on again 🔌.
- **End Reached** fires when the reconnect limit runs out (3 by default, you can set it from Blueprint).

The demo's URL screen shows all of this as on-screen text.

The multiple open-close test is where it got less fun. Memory went up with every open and close, about 0.5 MB each time, in a straight line. I spent a day chasing it, couldn't pin it down, and with the deadline this close I parked it as a known issue. It comes back at the [end of this devlog](#two-rabbit-holes).

### Small but visible

Other pending updates included reporting the video track and its information. `GetNumTracks` was returning 0, so Blueprint couldn't read the video's size, frame rate or codec. Now it can (1280x720, 25 fps, "hevc").

The colours were also slightly off. Remember the `yuv420p(tv)` in the ffprobe output from [#3](/devlogs/2026/09/05/ipstream_3.html)? The `tv` part is the colour range. What's missing after it is the colour formula, because the camera didn't specify which one it uses. When it's not specified, FFmpeg's converter falls back to **BT.601**, the SD standard. HD video is usually **BT.709** _aka Rec.709_ and mostly all videos are at least HD nowadays. So I switched the default fallback to BT.709 instead when nothing is specified and it made the picture match the same stream running on VLC, side by side.

### A first latency number, the awkward way

The last thing for v0.1 was a latency number, since "as low latency as possible" was the whole point back in [#1](/devlogs/2026/08/23/ipstream_1.html). My CCTV camera is fixed and far away from the PC, so the setup was a bit hacky: a phone showing a millisecond clock on a world-time website held in front of the camera, a browser running the same clock website on my PC next to the game window, and a lot of screenshots. **About 250 ms from camera to screen** (median 248 ms over 25 screenshots). Call it rough, though. The mobile display was not very clear in the CCTV footage so I asked Claude to try and figure out the numbers and it did everything it could to read those blurry digits.

> For all future tests I figured it would be a lot easier to just use a local RTSP server and OBS to do all the tests, so that's what I did :). _Also sharing screenshots wouldn't doxx me this way._

## Two rabbit holes

After the expo I took a couple weeks break from this project and worked on the [Chrono Recall](/projects/chrono-recall) gameplay ability prototype. I came back around mid-Nov to the two things I'd parked: the leak, and a proper breakdown of where the latency goes. OBS made both a lot easier. It runs on the same PC, so there's no dependency on the camera and nothing private on screen.

**The leak.** Memory grew by 3 to 15 MB a minute while a stream was open, outside Unreal's own allocator. Chasing it took a stand-alone test program, a 12 GB heap trace and a lot of wrong guesses. Spoiler: it wasn't a bug in my plugin.

**Where the milliseconds go.** With Unreal Insights (Unreal's profiler) I timestamped every frame at four points along the way, to see how much of the delay is actually the plugin's. With OBS I could also measure the whole trip from source to screen properly this time, no phone clock needed. One OBS setting turned out to matter more than anything in my code, and B-frames made an appearance too.

That work went out as [`v0.1.3-beta`](https://github.com/LifeisaRepo/UE_IPStream/releases/tag/v0.1.3-beta){:target="\_blank"} on 17 Nov, with a Shipping demo, a Development demo for profiling and a UE5.3 plugin package as well.
